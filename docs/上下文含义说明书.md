## Foreshadow 动态上下文系统

`Foreshadow` 是光标预测子系统的核心数据结构（原名 `DynamicContext`，已更名），负责组织和维护所有上下文项，并向推理引擎提供统一的 Prompt 序列化接口。其设计理念是：**用尽量少的 token 覆盖尽量大的召回空间**。

当前共有 **七个上下文项**，当内含代码段存在重复时的去重优先级排序：

```plain
CursorContext > AttentionZone > SoftRelContext > KeywordContext > LastArtifactContext > History
```

以下逐一说明各上下文项的设计动机、技术实现和在 Prompt 中的呈现方式。

---

### 1 CursorContext（光标上下文）

#### 设计动机

光标当前所在的位置是最直接的编辑现场，也是推理"是否需要跳转"的起点。如果当前行代码不完整，模型应优先预测原地补全；如果当前行代码完整，则需要决定是否跳转及跳转目标。

#### 实现

由 `updateByCursor(cursorPosition)` 驱动，每次光标位置变化时异步更新：

```typescript
// foreshadow.ts
async updateByCursor(cursorPosition: vscode.Position) {
    const curCodeWindow = await vmRepoMap.getCodeSnippet(
        cursorContextLocation, true, 
        cursorContextSize.upToLines,   // 向上 20 行
        cursorContextSize.downToLines  // 向下 40 行
    )
    this.cursorContext = new CursorContext(
        cursorContextLocation, curCodeWindow,
        cursorContextSize.upToLines, cursorContextSize.downToLines,
        editor.document
    )
}
```

`CursorContext` 继承自 `ArtifactContextItem`，在代码窗口中精确标注 `<|Cursor_Position|>` 标记，使模型知晓光标的准确行。

### 2 Task（当前任务意图）

#### 设计动机

任务意图是"语义级"的伏笔。开发者在执行某个任务时，其下一步编辑往往在语义上与任务强相关。Task 上下文能帮助模型理解"为什么"要跳转，从而在多个候选位置中选择最符合任务语义的目标。

#### 实现

`TaskRecognizer` 定期（默认每 60 秒）分析近期行为日志，通过 LLM 聚类并识别当前任务，产出 `Task` 对象（任务名称 + 任务描述 + 关联 LogItem 列表）。

`Foreshadow` 取最新的一个 Task：

```typescript
// foreshadow.ts
updateByTask(globTasks: Task[]) {
    this.task = globTasks[globTasks.length - 1]
}
```

当 `global.tasks` 更新时，`global.addTasks()` / `global.setTasks()` 会自动调用 `CursorPredictor.updateTask(tasks)`，保证 Task 上下文的实时性。

#### Prompt 呈现

### 3 AttentionZone（注意力区域）

#### 设计动机

启发自 Cursor IDE 记录开发者最近打开过的 20 个文档。AttentionZone 记录了开发者光标近期掠过的所有文件与代码片段，代表开发者的"视野范围"——这些位置有很大概率是下一步的编辑目标。

#### 实现

每次光标位置变化时，`updateAttentionZone()` 被异步调用，将当前光标位置的代码片段追加到注意力队列：

```typescript
// foreshadow.ts
private async updateAttentionZone(uri: vscode.Uri, cursorPosition: vscode.Position) {
    const codeSnippet = await vmRepoMap.getCodeSnippet(cursorContextLocation, true)
    this.attentionZone.push(new ArtifactContextItem(cursorContextLocation, codeSnippet))
    // 内部去重后裁剪队列大小
    ArtifactContext.deduplicateFieldArray(this.attentionZone);
    ArtifactContext.trimFieldArray(this.attentionZone);
}
```

AttentionZone 是一个 FIFO 滑动窗口，内部去重后保持固定容量（由可配置全局变量 `ArtifactContextItemMaxSize` 控制），使其只记录"最近的注意力轨迹"。

### 4 LastArtifactContext（硬关系工件上下文 Explicit Association Context）

#### 设计动机

开发者最近一次编辑的代码工件（LastArtifact），在代码依赖图上与若干其他工件存在明确的静态关系（引用、被调用、类型定义等）。这些具有硬关系的工件是下一步跳转的强候选位置，能显著提升召回率。

#### 实现

由新日志事件驱动，在 `updateByLog()` 中找到最近一次编辑的工件，并异步调用 `vmRepoMap.getArtifactContext(lastArtifact)` 获取其完整工件上下文：

```typescript
// foreshadow.ts
private async updateLastArtifactContext(lastArtifact: Artifact | undefined) {
    const lastArtifactContext = await vmRepoMap.getArtifactContext(lastArtifact)
    this.lastArtifactContext = lastArtifactContext
    this.lastArtifactContext.forEach(ac => ac.trim()) // 裁剪超长片段
}
```

`VMRepoMap.getArtifactContext()` 会沿着工件的 AST 层级路径（hierarchy）逐节点查询，每个节点的上下文包含：


| 上下文类型             | 适用工件类型               | 说明             |
| ----------------- | -------------------- | -------------- |
| `ImportBlock`     | File                 | 文件的 import 语句块 |
| `Documentation`   | Function / Method    | JSDoc / 注释文档   |
| `TypeDefinition`  | Variable / Parameter | 类型定义位置         |
| `References`      | Function / Class     | 被引用位置列表        |
| `Implementations` | Function / Interface | 实现位置列表         |
| `Callers`         | Function / Method    | 调用者位置列表        |
| `Callees`         | Function / Method    | 被调用位置列表        |
| `Members`         | Class / Interface    | 成员列表           |


所有查询均通过 `ArtifactContextProvider` 调用 VSCode LSP 实现，并配备两级缓存（上下文缓存 + 代码片段缓存）加速响应。

### 5 SoftRelContext（软关系上下文 Implicit Association Context）

#### 设计动机

并非所有代码跳转都能被 LSP 的静态分析捕获。例如：

- 国际化文件（`zh-CN.json`）与页面组件（`Page.tsx`）之间没有 import 关系，但开发者在添加新文案时必然在两者之间来回跳转
- 同一功能的 mock 文件与接口定义文件
- 测试文件与被测模块

**软关系**是指：通过观察开发者的**光标回环跳转行为**，自动发现并持久化这类"隐性关联"。

#### 软关系的发现：`SoftRelObserver`

核心算法是检测 **A → B → A' 回路模式**：

```typescript
// observer.ts
private isLoopPattern(pointA, pointB, current): boolean {
    // 1. 时间约束：整个回路必须在 5 分钟内完成
    if (current.timestamp - pointA.timestamp > softRelLoopTimeWindow) return false;
    // 2. 距离约束：A 和 B 必须有显著距离（跨文件 or 同文件行号差 > 30）
    if (!this.isSignificantDistance(pointA, pointB)) return false;
    // 3. 回路约束：当前点必须回到 A 附近（允许几行误差）
    if (this.isNear(pointA, current)) return true;
    return false;
}
```

检测到回路后，先通过 `VMRepoMap.getEdgeType()` 查询两个工件之间是否存在**硬关系**（定义、调用、实现、包含等），**只有排除了硬关系**后才认定为软关系，交由 `SoftRelationMap.updateSoftRel()` 更新。

防抖机制：光标必须停留 800ms 以上（`softRelDwellThreshold`）才被认定为"稳定停留点"，避免快速滑动触发误判。

#### 软关系的存储：`SoftRelationMap`

软关系以 `SoftRelation` 对象存储，持久化为 JSONL 文件（`.virtualme/soft-rel.jsonl`），支持：

- **频率权重**：记录每日触发次数，计算关系强度（`DayFreq` 滑动窗口，默认 30 天）
- **节点合并**：当新触发点与已有关系重叠率 ≥ 0.5 时，执行节点范围合并（`mergeNodes`），防止同一关系的细微变化产生大量碎片条目
- **过期清理**：连续 10 天无触发的关系自动过期删除（`cleanExpiredRelations`）
- **内存索引**：以 URI 为键的哈希表（`SoftRelQuerier`）加速查询，无需全表扫描

#### 查询

`Foreshadow` 同时查询**最近编辑的工件**和**当前光标位置**的软关系，并发获取：

```typescript
// foreshadow.ts
const [lastArtRels, cursorRels] = await Promise.all([
    this.updateLastArtifactRels(lastArtifact),
    this.updateCursorRels()
]);
```

Top-K 结果（默认 K=3）按综合得分（重叠比例 × 频率权重）降序排列。

#### 与规则引擎的衔接

每个仓库持久化的 **软关系表**（`SoftRelationMap` / `.virtualme/soft-rel.jsonl`）除服务 SoftRelContext 召回外，还向**直觉规则引擎**提供跨文件选型先验：规则侧以结对导航范式（FilePairNav）消费「当前文件 → 偏好伙伴文件」关系，与前端软关系图谱承担同一任务——刻画 LSP 硬关系之外的互补模块跳转（如 locale↔UI、types↔impl、核心模块簇）。关系可随使用时长由 `SoftRelObserver` 观察更新；规则引擎离线实验中的 `FILE_PAIR_HUBS` 即该表的可配置投影。详见 [第 9 节](#9-foreshadow-直觉规则引擎)。

### 6 KeywordContext（关键词上下文）

#### 设计动机

LSP 硬关系只能捕获已经被导入或调用过的工件；软关系只能捕获历史上有过来回跳转的工件。而实际开发中，开发者可能需要跳转到**当前上下文中出现过的标识符**所定义的位置，例如：

- 光标附近代码使用了某个 TypeName、FunctionName，其定义可能在项目其他文件中
- 最近的编辑/选中操作涉及到了某些语义关键词，其相关实现散布在多处

KeywordContext 通过**从当前光标上下文和编辑历史中提取项目级语义关键词，全局 ripgrep 搜索这些关键词**，将搜索命中的代码位置作为额外的召回上下文，覆盖 LSP 静态分析和软关系无法捕获的跨文件语义关联。

#### 实现

`updateKeywordContext()` 由 `updateByCursor()` 触发，设有时间节流（`kwContextUpdateInterval`），避免每次光标移动都触发全局搜索：

```typescript
// foreshadow.ts
private async updateKeywordContext(): Promise<void> {
    const now = Date.now();
    if (now - this.lastKeywordContextUpdateTime < kwContextUpdateInterval) {
        return; // 节流：距上次更新未超过间隔，跳过
    }
    this.lastKeywordContextUpdateTime = now;

    let keywords: Keyword[] = []
    if (this.cursorContext) {
        keywords.push(...summonKeywordsFromCursorContext(this.cursorContext))
    }
    if (this.history) {
        keywords.push(...summonKeywordsFromHistory(this.history))
    }
    keywords = sortKeywords(keywords).slice(0, maxQuerykw); // 取 Top-K 关键词

    this.keywordContext = [];
    const searchResults = await Promise.all(
        keywords.map(kw => vmRepoMap!.grepAsContextItems(kw.keyword))
    );
    for (const items of searchResults) {
        this.keywordContext.push(...items);
    }
    this.keywordContext = ArtifactContext.deduplicateFieldArray(this.keywordContext);
}
```

#### 关键词提取与排序功能模块

关键词的**提取**和**排序**由专用的关键词提取功能子模块负责。

### 7 History（近期行为轨迹）

#### 设计动机

Task 是粗粒度的意图摘要，无法反映开发者最近几步的微观操作序列（切换到哪个文件、编辑了哪行、选择了什么代码）。History 弥补了 Task 在**实时性和粒度**上的不足，为模型提供最近几步的"操作现场"。

#### 实现

每次日志更新时，`updateByLog()` 经过以下处理链：

1. **合并编辑** (`mergeEditLogs`)：将同一工件内连续的细碎编辑事件合并为一个完整的 EditLog，避免噪声
2. **类型过滤**：只保留 `EditTextDocument` 和 `SelectText` 两类事件（与代码位置相关的行为）
3. **取最近 5 条**：`slice(-5)`

每条 LogItem 以行为单位序列化，编辑事件带有 Diff 标记（`<|before|>...<|after|>`格式）。
